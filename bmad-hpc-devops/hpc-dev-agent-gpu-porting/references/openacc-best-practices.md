# OpenACC Programming and Best Practices Guide — Applied to RegCM5

Source: https://openacc-best-practices-guide.readthedocs.io/en/latest/ — loaded by `evaluate-candidacy.md`, `port-routine.md`, and `validate-port.md` wherever a port escalates past `do concurrent` into OpenACC directives. The project's `do concurrent`-first policy (AD-3) governs *whether* to escalate; this guide governs *how* to write the OpenACC once escalation is justified — it does not override AD-3's escalation trigger.

**Assess before porting.** The guide's own first phase is baseline profiling to find real hotspots before touching any code — this is already this project's own discipline via `hpc-dev-agent-profiler`'s evidence requirement. The guide is not license to port anything that merely looks parallelizable; it still requires the evidence `evaluate-candidacy.md` already demands.

**Port incrementally, one kernel at a time, verifying at each step.** The guide's Porting Cycle is explicitly iterative — port one hotspot, verify it, move to the next — never a big-bang rewrite of a whole module's kernels in one pass. This matches the project's own case-by-case GPU-port-candidacy policy (AD-5): a "go" verdict on one routine is not license to escalate its neighbors without their own evidence and verdict.

**`kernels` vs. `parallel` construct.** `kernels` hands the compiler the parallelization decision — a safer default when loop independence hasn't been established, but the compiler can decline to parallelize a loop it can't prove safe, so its use requires checking `-Minfo=accel` to confirm it actually did, not just that it compiled. `parallel` asserts the loops are independent and forces parallelization — correct once the programmer, not the compiler, has already established independence (e.g. after ruling out pointer-aliasing per this project's own GPU-porting-hazards checklist). Default to `parallel loop` for RegCM5's confirmed hotspots, matching the already-merged pattern for `getcape`/`interp1d_r8`/`heatindex`; reach for `kernels` only where independence genuinely hasn't been established and the compiler's own analysis is a legitimate first check.

**Data locality — minimize host-device transfers.** This is the guide's central optimization axis, and the most common reason a GPU port compiles, runs, and produces correct results but shows no speedup. Structure data movement with a data region spanning the routine's full lifetime rather than a copy per kernel launch; use `copyin`/`copyout`/`create` deliberately rather than defaulting to a blanket `copy`; keep data resident on-device across repeated calls within a timestep instead of transferring it back every invocation. A port with a validated numerical tier but no data-locality analysis is only half-evaluated — profile it (back to `hpc-dev-agent-profiler`) to confirm the win wasn't erased by transfer overhead.

**Gang/worker/vector mapping and the `collapse` clause.** Map RegCM5's own iteration structure (the `(iy, jx)` 2D horizontal decomposition, typically with a vertical `k` loop) to the three OpenACC parallelism levels deliberately rather than accepting compiler defaults blind. A `collapse` clause across the horizontal indices is usually the right move when the vertical loop is short or carries a dependency, since it exposes more independent iterations to the gang/vector mapping than either horizontal loop alone.

**Pitfalls this guide warns against, directly relevant here:** porting before profiling (already excluded by this agent's own evidence requirement); moving all data to the device up front regardless of what a given kernel actually touches; assuming a `kernels` region that "compiled clean" means it parallelized — always confirm against `-Minfo=accel`, never a successful build alone.
