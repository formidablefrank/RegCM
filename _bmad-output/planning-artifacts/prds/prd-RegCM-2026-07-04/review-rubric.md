# PRD Quality Review — RegCM5 HPC Modernization (prd-RegCM-2026-07-04)

*Re-review after the targeted factual correction to Feature 4.3 / FR-9 / FR-11 / FR-35 / Risk Register / SM-12 / Open Question 11 (halo-exchange and GPU-porting-footprint scope). This supersedes the prior version of this file, which reviewed an earlier draft and whose findings (Feature 4.5 naming, FR-7/FR-11 unbounded qualifiers, the "second axis" gap in Vision, the SM-10/SM-11 numbering gap, the four Assumptions Index roundtrip mismatches) have all since been fixed in the current `prd.md` — verified during this pass.*

## Overall verdict

The targeted correction is executed carefully where it was aimed: FR-11 and FR-35 are explicitly cross-signposted in both directions ("tracked as its own FR"), the original four-hotspot findings (getcape 54%, CLM-hydrology memset ~20%, `interp1d_r8` ~12%, `heatindex` ~8%) survive untouched and uncontradicted everywhere they recur, and every file path, commit reference, and directive count I spot-checked against the actual repository (`Main/mpplib/mod_mppparam.F90`'s 198 `!$acc` lines, `Main/mod_moloch.F90`, `Main/radlib/mod_rad_colmod3.F90`, the Everett@NVIDIA/Fatica commit history) checked out. What the correction did *not* do is reconcile the much bigger fact it surfaced — that OpenACC is already the dominant, merged accelerator pattern across ~90 files — with the PRD's pre-existing "do concurrent-only" strategic narrative in the Vision, Glossary, and Non-Goals, which now reads as flatly false rather than merely dated. Two smaller but concrete cross-reference slips also survived the correction pass: a wrong file path in the Glossary and a Success Metric that doesn't mirror the FR it's supposed to validate.

## Decision-readiness — adequate

Real trade-offs are stated as trade-offs, not smoothed: the RRTMG go/no-go framing (FR-9), the parallel-I/O-is-slower puzzle (FR-3/FR-34), and BMI's implement-vs-remove fork (FR-17, Open Question 1) are all live, unresolved decisions with named stakes. `[NOTE FOR PM]` callouts land at genuine tensions (FR-4's "don't skip it under schedule pressure," FR-27's "heaviest item in Phase 1, should be resourced/estimated as such"), not safe checkpoints. SM-C2 treats an RRTMG "no-go" as "a successful outcome of the investigation, not a failure to complete it" — a genuine counter-metric against sunk-cost pressure.

The correction's core weakness is a decision-readiness problem: a reader deciding how to resource Feature 4.3 would come away from the Vision and Non-Goals believing RegCM5's accelerator strategy is "`do concurrent`, with OpenACC only as a fallback investigated case-by-case" — when the PRD's own corrected FR-8 scope note says OpenACC is "the pattern actually merged" for the confirmed hotspots, and FR-11 documents 198 lines of production `!$acc` directives already governing the halo-exchange layer. See the full finding under Strategic coherence.

### Findings
- **critical** Accelerator-strategy narrative contradicts the correction's own evidence (§1 Vision, §3 Glossary "OpenACC" entry, §5 Non-Goals) — flagged in full under Strategic coherence; noted here because it directly undermines whether a decision-maker can trust the PRD's framing of Feature 4.3's risk profile. *Fix:* see Strategic coherence finding.

## Substance over theater — adequate

NFRs are specific and product-grounded (Cross-Cutting NFRs names exact bounds — `rMAD`/`rRMSE` thresholds, "zero overhead to non-DEBUG builds" — not "must be performant"). No persona theater: three UJs, each a single grounded sentence, explicitly justified as the right weight for solo-paced infrastructure work. No innovation theater or differentiation-section padding.

### Findings
- **high** Vision theater: the Vision statement's claim of "a disciplined `do concurrent`-only accelerator strategy" (§1, echoed verbatim as Feature 4.3's opening sentence) is stated as descriptive fact about the current codebase, but two paragraphs later (§4.3) Feature 4.3's own correction paragraph documents "`!$acc`/`do concurrent` directives in 90 files (1,476 lines)" including "a working GPU-direct exchange implementation" in the halo-exchange layer — i.e., OpenACC is not merely tolerated, it is the actual merged pattern for most of what's already in the tree. The Vision line now reads as aspirational strategic-intent copy the correction should have qualified. *Fix:* Add a clause to the Vision sentence and Feature 4.3's opening line distinguishing "this program's own new work defaults to `do concurrent`" from "the codebase already carries substantial NVIDIA-contributed OpenACC work predating this policy."

## Strategic coherence — adequate

The thesis ("evidence over guesswork," §1) genuinely drives feature prioritization — Phase 1 is profiling/regression infrastructure precisely because later phases' decisions (FR-9's go/no-go, FR-34's I/O recommendations) depend on it — and the program's release/distribution work (containers, CI) is explicitly tied back to the same thesis ("they are the infrastructure that makes every other claim in this program checkable... not a separate modernization agenda," §1). Counter-metrics (SM-C1, SM-C2) validate the thesis rather than measuring activity.

### Findings
- **critical** The "`do concurrent`-only" strategic bet is now internally contradicted by the correction it received. Three passages assert or imply OpenACC is unused-by-default / escalation-only:
  - Glossary, §3: "**OpenACC** — ...configured as available...but currently unused (**zero `!$acc` directives in the tree**). Escalation path if `do concurrent` proves insufficient."
  - Non-Goals, §5: "**No full OpenACC (or CUDA Fortran) rewrite.** `do concurrent` remains the primary and default parallel-loop construct; OpenACC is only escalated to where FR-9-style investigation shows `do concurrent` insufficient."
  - Vision, §1 / Feature 4.3 opener, §4.3: "a disciplined `do concurrent`-only accelerator strategy."

  All three are flatly contradicted by content the correction itself added or left standing nearby: Feature 4.3's correction paragraph (90 files / 1,476 directive lines), FR-8's scope note ("the four hotspots already ported under FR-35 use OpenACC directly...the pattern actually merged, per `project-context.md`"), and FR-11's body (198 `!$acc` lines in `mod_mppparam.F90`, including `!$acc data copyin/copyout` and `!$acc host_data use_device` patterns). I verified independently against the repository: `Main/mpplib/mod_mppparam.F90` carries exactly 198 `!$acc`-tagged lines, and git history includes a commit ("Everett @NVIDIA") explicitly converting `do concurrent` loops *back* to `do` + OpenACC directives for performance — the opposite direction from what the Glossary/Non-Goals state as policy. This is the PRD's own account of its central technical strategy failing to survive contact with its own corrected content, not a stale peripheral detail. *Fix:* Rewrite the Glossary's OpenACC entry to separate current reality (substantial existing NVIDIA-contributed OpenACC use, itemized by FR-35) from forward-looking policy (this program's own new work prefers `do concurrent`, escalating only where shown insufficient). Apply the same split to the Vision sentence and the Non-Goals bullet.

## Downstream usability — adequate

FR/SM/UJ IDs are contiguous and gap-explained (FR-36 retirement, SM-10/SM-11 non-assignment/retirement, both narrated inline). The §0 note about FR-33–38 being non-sequential pre-empts confusion about numbering.

### Findings
- **high** Glossary "Halo exchange" entry (§3) cites the wrong file: "The MPI communication pattern (`exchange_array_r8/r4` and related routines in `Share/mod_mppparam.F90`)..." The actual file (confirmed against the repository) is `Main/mpplib/mod_mppparam.F90` — the same path FR-35's corrected text uses ("the halo-exchange layer (`Main/mpplib/mod_mppparam.F90`...)"). FR-11's own "Corrected from an earlier draft" sentence repeats the stale `Share/` path before its later sentences correctly drop the prefix. Since the Glossary is the canonical term source FRs are supposed to resolve against, a downstream reader who trusts the Glossary over FR-35 will look in the wrong directory. *Fix:* Correct the Glossary entry and FR-11's first sentence to `Main/mpplib/mod_mppparam.F90`.
- **high** SM-12 ("Validates FR-37") doesn't match what FR-37 itself says it covers. FR-37's own consequence bullet states: "New GPU-porting work under this program (FR-9, FR-10, **FR-11**) is held to these same thresholds by default." SM-12's text says the regression test is "applied consistently across every already-validated GPU-ported subsystem found by FR-35's full-repository audit (not only the original four) **and any new GPU-porting work under FR-9/FR-10**" — FR-11 is missing even though FR-37 names it explicitly, and FR-11 (halo exchange) is arguably the highest-stakes item to hold to this bar since it affects every field, not one subsystem. Looks like SM-12 was updated for the FR-35 rescoping without being re-synced to FR-37's FR-9/FR-10/FR-11 list. *Fix:* Add FR-11 to SM-12's enumeration to match FR-37's consequence bullet.
- **medium** Phase 3 (§6 Phased Scope) still glosses FR-35 by its pre-correction scope: "FR-35 (verify and document **the source thesis's existing GPU ports** — confirmed already merged; a documentation/verification task, not re-implementation)." This describes the four-hotspot scope FR-35 had before this correction, not the "full repository footprint" (90 files, 1,476 lines) FR-35's own rewritten body now covers. A reader who consults only Phased Scope (a plausible standalone read) would materially undersize FR-35's actual workload. *Fix:* Update the gloss to "verify and document the full existing GPU-porting footprint (90 files, 1,476 directive lines), not only the source thesis's four documented hotspots."
