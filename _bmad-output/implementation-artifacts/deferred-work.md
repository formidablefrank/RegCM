- source_spec: `_bmad-output/implementation-artifacts/spec-regcm-io-mode-benchmarking.md`
  summary: Multi-login-node HPC clusters (like Leonardo) make `nohup`/`disown`/`setsid`-detached background driver scripts unreliable to track and kill from a fresh session — worth a project-level note (or a small PID-file + hostname-stamped lockfile convention in shared tooling) so future long-running sweep drivers can be found and stopped from any login node instead of accumulating untraceable zombies.
  evidence: `submit_sweep.sh` was launched from a terminal that landed on `login01`; a later session's terminal landed on `login05`. From `login05`, `ps -ef`/`pkill -f` never found the `login01` process (different node, same shared filesystem/SLURM controller, but processes aren't visible cross-node), and `ssh login01`/`ssh login01-interconnect-1` both failed with `Permission denied` (no passwordless inter-login-node auth for this account). The result: at one point *two* independent driver instances were alive simultaneously (one per login node), racing for the same `dcgp_qos_dbg` MaxSubmitPU=1 slot and causing several confusing `sbatch` rejections and one `pkill -f submit_sweep.sh` that self-terminated the invoking shell (the pattern matched the wrapping shell's own command line, not just the target). Root-caused via `scontrol show job <id>` → `AllocNode:Sid=login01-interconnect-1:...`, which is the only way the discrepancy became visible. Eventually resolved by standing down from competing submissions and letting the `login01` instance finish the remaining combos, monitored via `squeue`/`sacct` (cluster-wide, visible from any login node) rather than `ps` (node-local).
